Duplicate rows from non-idempotent load confidence: high

Explains: duplicates.order_id

Facts (from evidence)

  • 25 duplicate key rows in target [duplicates.order_id]
  • Context mentions a retried load [changelog.md]
  • Load mode is APPEND [etl_transform.sql]
  • Load mode is APPEND [metadata.json]
  • Source keys are unique, so duplicates were introduced by the load [duplicates.order_id.source]

Likely root cause: A load was re-run in append mode, inserting part of a batch twice.

Assumptions

  • The retry is the only re-run in the window

Next steps

  1. Count duplicates by load batch/ingestion timestamp
  2. Switch the load to MERGE on the primary key
  3. Deduplicate the affected partition

Source rows dropped by transform confidence: high

Explains: keys_missing_in_target, record_count

Facts (from evidence)

  • 40 source keys absent from target [keys_missing_in_target]
  • All missing rows have quantity between -3 and -1 [keys_missing_in_target]
  • Transform filters on quantity > 0 [etl_transform.sql]
  • Net row difference -15 = -40 dropped + 25 duplicates [record_count]

Likely root cause: The filter `quantity > 0` in the transform removes these rows.

Assumptions

  • The dropped rows are valid business records (e.g. refunds)

Next steps

  1. Confirm with the data owner whether these rows should be excluded
  2. If not, remove or narrow the filter and backfill

NULL customer_id in target confidence: high

Explains: missing_values.customer_id

Facts (from evidence)

  • 122 NULL customer_id values in target [missing_values.customer_id]
  • customer_id is taken from a LEFT JOIN to warehouse.dim_customer [etl_transform.sql]
  • Context records a change to dim_customer [changelog.md]
  • Context records a change to dim_customer [metadata.json]

Likely root cause: A key change in dim_customer breaks the join, so unmatched rows get NULL customer_id.

Assumptions

  • Missing values are not present upstream

Next steps

  1. Query unmatched customer_id values against the dimension
  2. Update the join to the new key format or add a mapping table

revenue mismatch confidence: high

Explains: value_match.revenue, rule.revenue_formula

Facts (from evidence)

  • 474 rows differ; target/source ratio median 1.08 (range 1.0799–1.0801) [value_match.revenue]
  • All mismatched rows have currency = EUR [value_match.revenue]
  • Transform has special handling when currency = 'EUR' [etl_transform.sql]

Likely root cause: The transform converts revenue for EUR rows, but source revenue is already converted (double conversion).

Assumptions

  • The rate used equals the observed ratio

Next steps

  1. Compare revenue for a few EUR orders at each pipeline stage
  2. Remove the duplicate conversion and reprocess affected dates
